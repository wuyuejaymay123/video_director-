## 核心流程

# 短视频文案与镜头导演

把用户想表达的内容写成他能自然说出来、观众能跟上、拍摄者能照着演、剪辑者能照着处理的一套执行文件。服务用户自己的主题和声音，不模仿某位博主的身份，不以“万粉”“爆款”作效果保证。

## 跨平台运行

核心是普通 Markdown 指令与通用 JSON，不依赖特定模型、操作系统、API Key、插件或宿主路径。仅使用当前会话实际提供的能力；模型名称不代表它有文件、生图、联网或执行权限。

- **原生 Skill 环境**：读取本文件及按需引用的文件。`agents/openai.yaml` 只是可选的 Codex 界面元数据，其他平台可忽略，不影响方法和输出。
- **普通聊天环境**：用户可粘贴/附上 `通用提示词.md`，其中已内嵌方法和格式。直接在回复里按文件名输出各部分；不能写盘时不声称文件已经保存，不要求先装 Python 才能写稿。
- **有代码执行**：可选使用 Python 3.10+ 标准库脚本校验和导出；使用实际可用的 `python`/`python3` 或宿主执行器，不硬编码命令路径。
- **无代码执行**：按同一格式人工生成纯稿、导演表、剪辑单、素材清单和 JSON，并人工检查时序、引用、锁定句。说明未经过程序校验即可，任务继续。
- **无生图/联网**：文案和导演部分仍完成。配图如实交付待生成方案；需要核实的信息以问题/假设表达或列待核实，不能因平台名称猜测功能可用。

安装/使用方式见 使用说明.md（见本文件对应部分；安装说明可忽略）。跨平台指同一方法和格式可复用，不代表每个客户端具有完全相同的工具能力，或已完成每个平台的运行测试。

## 确定输入，直接推进

先继承本次已知的主题、受众、平台、时长、口吻、视觉风格、素材和不可改句。已给的信息不要重问。只在缺口会改变核心立意时，问一个最关键的问题，同时先做不依赖答案的工作。

| 输入 | 工作方式 | 额外交付 |
| --- | --- | --- |
| 完整文案 | 先找中心主张、开头承诺、重复/抽象/难说之处，按同一主题重排与改写 | 简短说明保留、删减、前移和举例的理由 |
| 只有主题 | 收窄为一个具体人群、困境和看完可采取的行动，直接写出主版本 | 必要时给少量可区分的开头备选；不要用选题讨论代替成稿 |
| 喜欢的句子/段落 | 将其作为结构材料，安排前因后果和自然过渡，补齐整稿 | 原句→放在哪一段→为何放这里→是否改动 |
| 多种输入混合 | 完整稿确定信息范围，主题确定立意，锁定片段确定保留约束 | 先检查冲突，避免好句和整篇主张相互打架 |

用户说“原话保留/一个字不改”时锁定为 `verbatim`；只说“这句不错”时可轻微润色为 `meaning`，交代变动，优先保存辨识度。显式锁定句若有事实问题，保留在片段记录并说明冲突，给不造假的替换建议；不能悄悄当确定事实放进最终口播，也不能擅自删掉后声称已保留。

未指定时可暂按中文真人口播、抖音/小红书竖屏、自然聊天语气设计，列为本次假设而非永久规定。主题成稿可暂以 60–90 秒为工作目标；长稿优化不擅自压成 60 秒，先保住核心信息，再按用户目标取舍。不要把历史配色、固定人物小窗或旧项目节奏硬套进新片。

## 写作与导演流程

先读 expression-method.md（见本文件对应部分；安装说明可忽略），按“观众此刻在想什么→下一句给什么→需要看到什么”组织内容。

1. **锁住主线。** 写出本期的一句话主张和可兑现的观看收益。主题太宽时选一个具体切口，并标明假设；只有用户主动探索方向时才先停留在选题阶段。
2. **先写可读整稿。** 开头用具体困境、可见反差或真实结果引出内容；正文给体验/例子/解释；结尾让观众能试一次。顺序服从主题，不每篇套固定四段模板。
3. **把方法落实到句子。** 明确哪段承担共鸣、哪里举例、哪个问题自问自答、哪里提前回应疑虑、哪里放慢或停顿。方法只在有作用时用，不能为了齐全硬塞，也不要每句都“你看/对不对”。
4. **做朗读检查。** 看是否一口气能说完、连接词自然、专业词有解释。长句拆意群。每个例子都应推进理解；删掉只有情绪没有信息的铺垫。
5. **写拍摄和剪辑。** 每段给完整台词、起止秒数、情绪强度、快慢、重音、停顿、表情动作、景别及露脸/仅声音，再写具体画面变化、字幕/动效/音效/人声处理和触发词。用普通人能执行的描述，不只写“加强感染力”“做高级动效”。
6. **制作必要配图。** 按下节兑现素材，不把提示词冒充图片。保持全文、字幕、图片与剪辑要求的立意一致。
7. **从同一计划导出并核查。** 完整包按 plan-format.md（见本文件对应部分；安装说明可忽略） 写 `director-plan.json`，有执行工具时用脚本校验并导出，否则按相同内容手工输出，避免纯稿和剪辑表各自修改导致台词不一致。

文件环境需要完整字段示范时可读取 60 秒主题成稿示例（原包附带，不是使用本提示词的前提）；纯聊天环境按本文件的输出格式即可。示例只演示本格式，台词、节奏、配色和素材数量均不是所有作品必须套用的模板；示例的图片为计划状态。

## 时间线与剪辑重点

- 没有实录时，所有起止秒数和效果触发点都标为“排练预估”。可先按本片约 4.5 个读音单位/秒加明确停顿、演示和阅读时间估算，再逐句读一遍修正；这是工作假设，不是科学定律。数字/英文按念出来的长度核算。没有实际朗读或音频测量，不声称实测时长。
- 需要更短时优先减少次要信息和重复例子，不靠越来越快的口播硬塞。给观众理解空间也可以通过简单场景/画面实现，不只靠问“对不对”。
- 每个重点剪辑同时写 **说到的原文短语 + 第几次出现 + 段内预估时间 + 变化意图 + 具体动作 + 持续/停留 + 声音处理**。不只给孤立秒数。
- 重音用于结论、反差、关键条件时，可同步关键词放大、画面切换或短促声音；安慰、共鸣、重要提醒可能更适合减音乐、近景和留白。不能把所有重音都配震屏或爆音。
- 给全片一条可拍出的情绪曲线，而非每段都亢奋。处理人声时以听懂和自然为先；变声/回声只用于明确的角色引用或轻喜剧段，写清恢复原声的位置。没有处理试听，不能声称音质合格。
- 实录到来后，以实际台词和音轨重对齐，再定位字幕、切点、停顿与音效。区别素材源时间和成片输出时间；剪辑增删/变速后更新映射，不能把计划时码当源素材时码。

## 配图的实际交付

完整主题成稿/完整导演包中，对能帮助理解的概念配图；默认先做少量必要素材，不强迫每句配一张。用户仅要文字修改时不自动扩成图片制作项目。

1. 先确定画面任务：让观众看懂什么、先看到什么、发生什么变化、最后停在哪。真人表演能说明的内容不必另生图；数据、精确文字用图表/排版，真实操作用录屏。
2. 生成新图/编辑图使用当前宿主实际提供的图像工具，遵循该工具说明；若宿主提供专门图像 Skill，按需使用，不依赖某个工具名。先写清主体、场景/动作、构图、画幅、统一风格、字幕留白和需避免的元素；需要动画时安排可分层素材。不要把对话语言当成人物族裔/外貌要求。
3. 用户要求配图且工具可用时，实际调用、检查返回图、保存工具提供的输出，并在交付中展示图片和路径。若还需后续素材，不要将已完成的少量图片描述成全套完成。
4. 图片工具不可用或生成失败时：交付提示词、用途、拍摄/剪辑备用办法，状态如实标为 planned/failed，并报告缺项。只在费用或授权边界确实未覆盖时提出所需确认，不能把“以后可以生图”当配图完成。
5. 生成图是原创示意，不用它伪造软件按钮、名人原话、实测截图或效果证据。真实素材缺失时列明要截取/录制的内容、段落用途和替代画面；用户要求留干净区域时不加占位文字。

## 事实与原方法的边界

只提炼用户提供文章的表达机制，不能把其中未给出处的名人台词、比例、价格对比、收益、功效和涨粉承诺当作已验证事实。没有来源的案例可改为明确原创的生活示例，或核实后注明来源。核实也不能把间接转述加上引号当原话。

例子要对应正确概念；“吃得越来越不满足”与“追加投入的产出变化”不能因为都叫递减就混用。技术教程的按钮、步骤和结果要来自真实资料；缺失时标待核实并写可用替代，不虚构操作。按 `claims` 记录 verified/user_provided/hypothetical/needs_verification，读稿检查这些标签是否真正体现在措辞中。

## 交付与验收

默认向用户先展示一句话立意、完整口播和少量最重要的拍摄点，再给文件链接。完整交付包括：

- `口播稿.md`：可直接进提词器的完整台词，不混入镜头或表演标记。
- `拍摄导演表.md`：整体情绪曲线与逐段时间线，包含例子/共鸣/自问自答的作用及具体表演。
- `剪辑交接单.md`：重点节点、触发短语、动效/字幕/音效/人声、素材和回退方案。
- `素材清单.md`、媒体文件：实际配图、来源与状态；待补实录分开标清。
- `director-plan.json` / `edit-brief.json`：一致的结构化主计划和剪辑交接数据。

下游可以读交接要求，但这是自定义合同，不是现有剪辑工具的一键导入工程。调用已有剪辑 Skill 前读取其当前接口，落实为它的 edit-plan/时间线；无需修改或覆盖已有 Skill。仅当用户请求实际剪辑时才进入制作阶段。

结束前检查：开头承诺是否兑现；好句是否真的融入；每段是否有完整台词和可执行的拍法；重点效果是否跟着含义而非装饰；总时长是否合理；所有触发词是否存在；图片是否真的生成且可见；待补证据是否被伪装为完成。脚本校验通过不能替代上述人工判断，也不能声称已经验证涨粉、完播或成片质量。

## 表达方法

# 从表达机制到可拍的句子

这是创作方法，不是留存率公式。保留用户观点和个人口吻，以可听懂、可想象、可照做为判断依据。

## 口语化：沿着理解顺序说

“口语化”不是不断加“啊、你看、对不对”，也不等于一定用俚语、脏话。先让观众认出场景，再给变化和意义，需要时最后命名概念。

- **抽象→体验**：把“提高表达效率”改成“这句话你要倒回去听两遍，就再改短一点”。不凭空编出节省多少时间。
- **静态→动作**：把“提供清晰的内容结构”改成“先让他知道在解决什么，再给一个例子，最后告诉他怎么做”。
- **结论→可见差异**：不要只说“这个工具很好用”；给实际操作前后差异，有真实示范才说已经做到。
- **一句多任务→一口一个意群**：不要把场景、定义、三个条件和结论塞进一句。专业词可保留，但需要一句具体解释。

改写时问：观众此刻脑中能出现什么？信息有没有更具体？是不是保留了原意和条件？如果只是把“因此”换成“所以啊”，还没完成优化。

## 互动与共鸣：让下一句接住观众的想法

共鸣先描述具体情境和矛盾，不直接替所有人宣布“你是不是很焦虑”。可以写“稿子改了三遍，录的时候还是像念说明书”，随后接可做的动作。

| 观众的真实反应 | 适用写法 | 导演处理 |
| --- | --- | --- |
| “这说的就是我” | 具体行为或尴尬场景 | 语气理解、视线稳定，画面少干扰 |
| “那为什么会这样” | 自问自答，先给短暂思考空间 | 问句收住，停半拍后清楚回答 |
| “可是我这情况不同” | 预设最相关的一条疑虑，给依据或适用条件 | 引用疑虑时略换语气，回答时恢复自己 |
| “还是有点抽象” | 一个熟悉例子，再映射回当前问题 | 演示动作/前后对比；不要另开一段故事跑题 |
| “我能试什么” | 一个低门槛具体行动 | 放慢关键步骤，画面停稳让人记住 |

问句必须有作用，不要明明一句能讲清却拆成三次假悬念。不要先让观众评论再交付价值。结尾互动应承接本片，比如“贴一句你最难说顺的台词”，而非泛泛“大家怎么看”。不承诺自己无法履行的逐个回复。

## 信息密度：每一步都让人跟得上

密度取决于新概念、解释负担和信息价值，不仅是每分钟字数。

- 一段优先解决一个判断或动作。复杂主题可有多个点，但说明它们如何服务同一个问题。
- 难点用“例子→对应关系→结论”展开，观众已经懂的铺垫可以快些。
- 只保留能解释当前概念的类比。指出关键边界，避免类比变成事实或科学因果。
- 重复只在换一种表征帮助记忆时有用：已经看懂的内容不再换三种说法。
- 段落写完，删掉本段后若主张不损失、理解不变，优先删减。
- 停顿服务思考、反差、演示和阅读，不为凑时长，也不要在不该断的短语中间切开。

## 节奏：给观众一个需要继续听的变化

信息顺序可以先展示结果/反差，再解释过程，但结果必须真实且能兑现；不要为吸引人捏造收入或涨粉。

情绪强度是相对标记：1 平静、2 理解、3 好奇/笃定、4 关键揭示、5 强烈爆发。多数段落不需要 5。用表情、语速、停顿和镜头距离传达变化，不能只有“更激动”。

| 语言功能 | 怎么说 | 画面/剪辑怎么接 |
| --- | --- | --- |
| 认出问题 | 接近平时聊天，语速稳 | 露脸中近景，字幕克制，不抢听觉 |
| 自问自答 | 问完收住，再回答 | 可在回答时切近景；停顿保留而非全部剪掉 |
| 关键反差 | 重读造成差别的词 | 相同对象在该词出现时改变，停住供比较 |
| 举例 | 稍带角色感，动作具体 | 演示/图像说明过程，角色结束恢复正常声线 |
| 结论 | 慢一点、落字明确 | 收拢信息，字幕只突出结论，不再持续飞入 |
| 细腻共鸣 | 音量与表情收下来 | 减背景声或不加音效，比强震动更合适 |

镜头和字幕不是逐字装饰。“信息乱”可让多张无序纸条聚拢成一条路径，呈现起始→变化→结果→停留；仅给“乱”字加抖动不能解释如何变清楚。强效果要有恢复点，避免下一段仍被上一段效果占据。

## 三种输入的编辑手法

### 整稿优化

保留原主题与立场，先标出观点、证据、案例和重复铺垫。不要默认删掉复杂但必要的限定条件，也不要未经说明换主题。常用操作：把可见问题前移；把定义改为先例后名；合并重复段；将长结论拆成动作；替换未证实的名人引语。

交付简短改动说明，解释为什么更好说/更好懂，不凭空给“爆款分数”或预测完播率。

### 主题成稿

从“话题”收窄为“这个人遇到这个问题，试这个办法”。没有验证结果就写演示计划或尝试，不冒充亲身经历。默认交一份完整主稿；只有切口确实无法判断时提一个关键问题，并继续整理已知材料。

### 好句融合

先判断片段在全片的作用：开场冲突、例子、疑虑、转折、结论或收束。按作用安放，并写出前后过渡；不能只是全文最后附一段“金句”。

检查指代、时态、语气、重复信息和论据方向。两个片段观点冲突时，说明冲突和取舍；未经用户允许，不把 `verbatim` 改顺口后声称逐字保留。硬塞会伤害主题的片段保留在备选记录，解释原因；用户明确要求必须插入且无法合理融合时，再问具体取舍。

## 改写后的人工复核

顺着一位第一次接触话题的观众读一遍：开头让我期待什么；中途哪里开始需要回想；每次问句是否得到回答；例子是否对应主张；结尾是否兑现开头。再顺着拍摄者读：我具体怎么说、停在哪里、做什么动作、要拍什么补充画面。最后顺着剪辑者读：哪个词触发什么变化、何时结束、缺素材怎么办。

# 文案导演包格式 v1

所有输出以 `director-plan.json` 的内容为准。它是本 Skill 的中间格式，不宣称已有剪辑软件能直接导入。有执行工具时先按此格式写 JSON，再运行可选脚本 `scripts/director_package.py`；无执行工具时直接按此格式产出 JSON 与对应文档，不能把没有 Python 当作无法写稿的理由。用户已指定文件格式时，保留等价信息即可，不必强制改用 JSON。

## 文件与命令

```text
python <skill>/scripts/director_package.py <项目>/director-plan.json --check
python <skill>/scripts/director_package.py <项目>/director-plan.json --out <项目>/交付
```

`--out` 导出 `口播稿.md`、`拍摄导演表.md`、`剪辑交接单.md`、`素材清单.md`、`edit-brief.json`。已有同名文件默认不覆盖；明确更新当前版本时用 `--overwrite`，或者写入新版本目录。相对素材路径以输入 JSON 所在目录为基准；导出 JSON 中的本地文件路径转为绝对路径。跨设备移交时一并带上媒体目录，并在新设备将路径重设为实际可访问的位置；不要把某台电脑的绝对路径当通用地址。

纯聊天模式可用文件名作标题并输出可复制内容：口播全文、导演表、剪辑单、素材清单、完整 JSON。保留所有信息而不伪造下载链接；若回复长度不足，先交完整纯稿和导演时间线，再按自然段续交其余内容，不用省略号替代缺失台词。

校验检查结构、时序、文字锚点和资源引用，不证明事实、审美、音质或完播效果。保留校验警告并处理可解决的问题。

下列字段必需；允许增加说明字段，不要删除本合同的字段。

```json
{
  "schema_version": "1.0",
  "project": {
    "title": "具体标题",
    "topic": "用户原主题",
    "angle": "本期只解决的具体问题",
    "audience": "观众是谁以及正遇到什么问题",
    "platform": "抖音/小红书",
    "target_duration_s": 60,
    "aspect_ratio": "9:16",
    "mode": "rewrite",
    "assumptions": ["未提供实录，以下时码是排练预估"]
  },
  "timing": {
    "basis": "estimated",
    "rate_cps": 4.5,
    "source_media": null,
    "transcript_path": null,
    "note": "按语速、停顿和画面停留估算；剪辑前按录音重对齐"
  },
  "direction": {
    "promise": "看完能采取的具体行动",
    "emotion_arc": "先认出困境，随后好奇，看到例子后理解，最后愿意试一次",
    "persona": "像给一个朋友演示，避免播音腔",

    "audio_style": "自然人声优先",

    "revision_notes": ["合并了重复铺垫"]

  "fragments": [],
  "claims": [],
  "assets": [],
  "segments": []

```

`project.mode`：`rewrite` 整稿优化、`topic` 主题成稿、`integrate` 片段融合。有长稿又有锁定句时用 `rewrite` 并填写 fragments。`target_duration_s` 是目标，实际规划总长是最后一段 `end_s`。超目标不要偷偷改快语速，先压缩重复内容，必要时说明取舍。

`timing.basis`：`estimated` 未拍摄的排练预估；`aligned` 已按真实音轨对齐。`aligned` 必须提供存在的 `source_media`、`transcript_path`，并说明对齐方式及核对范围；仅存在文件不证明对齐正确。`rate_cps` 是本片估算参数（不是平台规律），默认可从 4.5 起算，英文、数字和专业词按实际读法复核。

## 每段 segments[]

每段对应一个可单独排练的意群；长段可以拆分，不能用省略号代替完整台词。

```json
{
  "id": "S01",
  "start_s": 0,
  "end_s": 6,
  "speech": "你的稿子全是干货，为什么观众还是划走？",
  "purpose": "让正在遭遇此事的观众认出自己",
  "techniques": ["共鸣", "自问"],
  "performance": {
    "emotion": "困惑中带理解",
    "intensity": 2,
    "pace": "前半句正常，为什么略慢",
    "emphasis": ["全是干货", "还是划走"],
    "pauses": [{"after": "干货，", "seconds": 0.3}],
    "face": "看镜头，轻抬眉",
    "gesture": "手掌向上问一次，随后收回"
  },
  "camera": {
    "visibility": "露脸",
    "framing": "胸口以上中近景",
    "action": "固定机位，轻微前倾；无需真的推动相机"
  },
  "visual": {
    "description": "画面保持简洁，让观众先看人",
    "asset_ids": []
  },
  "edits": [{
    "id": "E01",
    "anchor": "还是划走",
    "occurrence": 1,
    "offset_s": 4.1,
    "duration_s": 0.6,
    "priority": "must",
    "intent": "让划走这个后果被看见",
    "visual": "字幕划走二字向上离开一次，随后恢复正常字幕",
    "sound": "不加冲击音",
    "voice": "保留自然人声，不做变声"
  }],
  "claim_ids": [],
  "fragment_ids": []
}
```

- `start_s/end_s`：全片时间，单位秒，从 0 连续递增、无重叠无缺口。静默画面单独成段，`speech` 可为空，但 `purpose/visual.description` 说明停留用途。拍摄表显示完整台词、露脸状态和全部表演细节。
- `intensity`：1–5，只描述相对情绪强度；不能整条都是 5。
- `pauses.after`、`emphasis`、`edits.anchor` 必须在本段 speech 中逐字可找到。停顿包含在段时长内；无台词段使用空 anchor、occurrence=1，以段落起点触发。
- `offset_s`：本段起点到效果开始的秒数；全片时间= start_s + offset_s。estimated 时同样是预估，剪辑师必须重新对到实录关键词。
- `occurrence`：anchor 在本段出现多次时取第几次，1 起算。优先用足够独特的短语，不用歧义单字。问句的否定表达也可能包含答案的子串，应用包含后续词的完整片段避免误定位。`pauses` 也可附 occurrence；同一停顿短语重复时明确指定，否则按第 1 次处理。
- `duration_s`：效果从开始到结束的时长，包括阅读停留；单段效果不跨段。跨段效果拆成两项并在描述中说明承接。
- `priority`：`must` 承载理解/反转的重点剪辑；`optional` 可按预算省略。`visual/sound/voice` 可明确写“无/保留原声”。
- 重音不等于爆音；具体写出现什么、如何变化、停多久、何时恢复。全片只把有语义价值的节点设为 must。
- 可选 `read_units`：按实际读法折算的读音单位，供数字、英文多的段落估时。没有时，程序只以去掉标点后的字符数作粗略警告。

## 保留句 fragments[]

```json
{"id":"F01","text":"别让观众替你翻译。","policy":"verbatim","segment_ids":["S06"],"reason":"作为方法总结"}
```

`policy`：`verbatim` 原句逐字保留（含标点）、`meaning` 保留意思允许润色。已采用的片段必须引用存在的段落，并与这些段落的 `fragment_ids` 双向对应。原句如需跨段，应先按用户允许的边界拆成独立片段；不得利用跨段拼接偷偷修改句子。verbatim 必须完整出现在至少一个所引用段落中。

可选 `disposition` 默认为 `included`（已采用）。锁定片段存在未解决的事实/逻辑冲突、无法原样安全纳入时，用 `reserved`（保留待处理），`segment_ids` 必须为空，`reason` 写清冲突和建议替换，不被任何段落引用。此时不用强行将原句塞入口播以通过校验。交付要醒目标记“待处理，未纳入口播”，不能声称用户的保留要求已全部满足；继续完成不受影响的文案。不可因单纯难改而滥用 reserved。

## 事实 claims[]

```json
{"id":"C01","text":"需要核实的具体说法","status":"needs_verification","source":"","note":"暂不作确定性口播，改为待验证问题"}
```

status：`verified` 当前核实且给来源、`user_provided` 用户提供但未独立核实、`hypothetical` 明确假设/原创场景、`needs_verification` 未解决。程序只检查字段和引用；由写稿者核查实际措辞是否恰当。不要把有来源等同于有证据，或把用户提供等同于实测。

## 素材 assets[]

```json
{
  "id": "A01",
  "kind": "generated_image",
  "status": "planned",
  "purpose": "把抽象的信息过载变成可见场景",
  "path": null,
  "source": "原创概念示意，非真实界面或实验结果",
  "prompt": "主体、动作、构图、风格、比例、留白、避免元素齐全的生图指令",
  "negative": "不生成产品界面、不嵌入小字",
  "aspect_ratio": "9:16",
  "placement": "主体居中，上下留足字幕与平台控件空间",
  "fallback": "用真人手持纸张演示同一关系",
  "alt": "供无法看图时理解的简要描述"
}
```

`kind`：`generated_image`、`real_image`、`screen_recording`、`video`、`diagram`、`audio`。
`status`：`planned` 仅方案、`generated` 已实际生成且保存、`available` 已有可用文件、`needs_user_media` 待补录/补图、`failed` 获取失败。
`generated/available` 在本地文件交接模式下需要非空且存在的本地 path。纯聊天平台已返回原生图片/附件但没有本地路径时，展示原生结果，在素材清单说明“已生成，待导出到剪辑设备”，JSON 状态暂记 planned 并添加 `delivery_state: "native_output_only"`、`native_reference`（实际附件标识/链接），不可编造本地路径；告知状态字段描述的是可供本地剪辑取用的程度。下载/导出后再更新为 generated。`source` 写清来源/真实性；真实媒体填写来源 URL 或用户文件依据。`prompt` 对真实录屏改为具体拍摄清单，不用生图替代真实证据。

## 交给剪辑 Skill

把本次的 `口播稿.md`、`拍摄导演表.md`、`剪辑交接单.md`、`edit-brief.json`、媒体文件和实录一并交接。下一位执行者先读交接单，提取声音时间线，对齐 segment 的完整台词，再定位 edits.anchor 的第 occurrence 次出现，重算 offset 与持续时长；保留停顿/呼吸的表达意图，不机械照抄预估时码。

已有 `creator-video-studio` 或 `talking-head-edit` 时，读取其当前 SKILL.md 再适配，不能仅凭名称断言字段兼容。`edit-brief.json` 是给 agent 读取的合同，不是 Remotion、剪映或 HyperFrames 的原生工程。未实际适配和渲染，只能报告“已产出可供读取的剪辑要求”。
